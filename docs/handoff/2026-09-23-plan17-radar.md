# Plan 17 handoff — radar scope

2026-09-23. Plan 17 is complete on `main`. The cockpit panel's `radar` slot —
reserved as a "RADAR / RESERVED" placeholder since Plan 6a (2026-09-15) — now
shows a rotating, heading-up sweep with fading contact dots and a
`Tab`-cycled 15/5/1 mi range. It is motivated directly by Mark's own playtest
of `pursuit-range` (Plan 7a): he got shot at, evaded, and lost track of the
AI contact with no way to find it again. Plan 6c structural overload and
Plan 7a AI pursuit were the prior handoffs; nothing about either slice
changed here.

## What landed

- `src/render/radar.ts` — pure math: `radarContacts` (bearing/range of every
  other airborne, non-parked aircraft against the player's own body axes,
  nearest-16 capped, deliberately with no epsilon floor on the forward
  component — the same behind-the-nose collapse Plan 7a's review found and
  fixed, copied here as the correct form from the start), a brightness/fade
  function with a non-zero floor, and the 15 → 5 → 1 → 15 range-cycle state
  machine.
- `src/input/` / `src/render/diagnostics.ts` / `src/render/main.ts` — `Tab`
  bound to `toggleRadarRange`, edge-triggered and working through a pause
  like the legend/mute toggles; a new `__ww2.radar()` diagnostics getter
  (`{ rangeMi, sweepRad, contacts }`); per-frame contact data threaded into
  `updatePanel` from the same `frame.world.aircraft` the `aircraft()`
  diagnostic already reads.
- `src/render/scene/radarScope.ts` / `panel.ts` — a TSL node material
  replacing the flat `MeshBasicMaterial` on the existing `radarFace` mesh,
  rendered into its own offscreen `RenderTarget` (the same shape
  `cloudShadow.ts` uses) and read back via `attachTo`/`update`/`readAt`,
  exposed diagnostically as `__ww2.radarPixelAt(bearingRad, rangeMi)`.
- `tests/render/radarScope.test.ts` — a headless, orientation-invariant test
  added in the Task 3 fix round (see below) so the shader's placement math
  has an automated guard that does not depend on the reference GPU.
- `tests/e2e/radar.spec.ts` — the reference-GPU acceptance spec (see below).

## Design boundary (deliberate, from the design doc)

Per the design doc §5, restated in the plan's Global Constraints, this slice
does not add: range rings or tick marks on the face; altitude-difference
cueing (range is horizontal-plane only); filtering by team or hostility (no
IFF exists in the sim — every airborne, non-player aircraft is a contact);
or persistence of the selected range across a restart or reload (defaults to
15 mi, like every other panel state).

## Two defects task review caught, both fixed on `main`

This plan's own review process is part of what shipped, not an
embarrassment to hide — per this repo's convention that a stale or
overclaiming doc is a defect worth fixing in the moment.

**Task 3: `readAt`'s diagnostic readback doubled the render-target's
uv-flip.** The shader's own placement math was hand-traced end to end and
confirmed correct (bearing 0 paints at 12 o'clock, +π/2 paints on the
pilot's right) — but `readAt` flipped the uv a second time, sampling the
vertically mirrored texel from what the shader actually painted. That is
correct only at bearing ±π/2 and silently wrong everywhere else, which would
have sent Task 5's reference-GPU run hunting in the wrong file. Fixed
(`62244db`) by extracting the placement math into a pure, tested
`scopeTexelFor` function and adding `tests/render/radarScope.test.ts` — a
headless guard against this exact class of bug that does not need the
reference GPU.

**Task 5: the brightness assertion was nearly unfalsifiable.** The design
doc's original acceptance criterion — and the plan's own Task 5 brief,
verbatim — called for `toBeGreaterThan(0.05)` on the pixel brightness at a
contact's position. `RADAR_FADE_FLOOR(0.12) * TRAIL_DIM(0.55) = 0.066` is the
ambient sweep trail's own floor, present at every point inside the circle
regardless of any contact, so 0.05 is cleared by pure background glow alone
— including, very likely, by the pre-fix double-flip `readAt` silently
reading the wrong (mirrored) location. The design doc's original claim that
a Tier 2 assertion would prove pixel placement was only actually true after
this fix. Replaced (`c9b16de`, `431bc08`) with a comparative, timing-
independent ratio check: brightness at the contact's own reported
bearing/range against the same bearing at a control range outside the dot's
radius. The shared `brightnessOf(bearing)` term cancels exactly, leaving a
fixed predicted ratio of 1/TRAIL_DIM ≈ 1.818 regardless of live sweep
timing. One instrumented run captured `atContact = 0.5333`,
`atFarSameBearing = 0.2980`, observed ratio 1.789 — strikingly close to the
theoretical 1.818, confirming the shader paints the dot exactly where the
math says.

## Remaining work

- Explicitly out of scope per the design doc §5: range rings/tick marks,
  altitude-difference cueing, team/hostility filtering (no IFF exists in the
  sim), range persistence across restart.
- `wrapPi` is duplicated between `radar.ts` and `controller.ts` — no shared
  home without touching `sim/`.
- The scope renders as a ~18% squashed ellipse (non-square face aspect vs.
  uv-space circle) — the design doc's aspect-ratio justification is
  backwards.
- `readAt`'s 4-texel-wide RGBA8 copy is an unnecessary carry-over from
  `cloudShadow`'s R8-specific constraint.
- Two `smoothstep(high, low)` reversed-edge calls (portability nit;
  `oneMinus(smoothstep(low, high, x))` reads the same and is unambiguous).
- `attachTo` leaks the fallback material and uses a loose `as Mesh` cast.
- `radarPixelAt` can throw a TDZ error if called before boot.
- `readAt` doesn't reject a negative/NaN `rangeMi`.
- `farRangeMi`'s `DOT_RADIUS` clearance isn't unconditional for a contact
  very near the selected ring's edge — inert for `pursuit-range`, worth a
  guard if this pattern is reused.
